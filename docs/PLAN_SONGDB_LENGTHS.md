# Song lengths from songdb

*Planned 2026-09-21, after A44 made the Amiga custom formats play. Not started. `docs/BACKLOG.md`
A52 is the entry; this is the reasoning and the steps.*

## Why now, when it was "mostly redundant" in September

`docs/reference/songdb.md` surveyed `mvtiaine/audacious-uade-tools` on 2026-09-07 and called its
song lengths mostly redundant: 165,000 of the 177,421 Modland files it covered were MOD, XM, IT and
S3M, and libopenmpt states a duration for every one of them. That was true, and UADE has reversed
it. An Amiga replay routine has no notion of a length and the file states none, so today:

- a tune shows no total and no slider for the **two seconds** it takes a second emulator to play
  it to the end in the background — measured on the phone, `amberstar (16).hipc`, 5:08;
- a tune that **loops** never gets one at all: the measurement reaches its ten-minute cap and gives
  up, which was 18 of 140 on the host corpus;
- every subsong switch starts a new measurement, and every played tune costs a few seconds of a
  core.

songdb was generated by audacious-uade — the same UADE, playing the same files — and records
per subsong how each one ended. Measured 2026-09-21 against the Modland index:

| | |
| --- | --- |
| Modland files the app offers through UADE that songdb lists | **3,792** |
| of those with a length | **3,792 — all of them** |
| agreement with our own measurement | to 0.1 s on all five checked, all seven subsongs of `cust.paradroid` |
| first subsong ending by the routine's own report (`p`) | 2,147 |
| first subsong ending in a **detected loop** (`l`) | 1,172 |

The second-to-last row is the one that decides it: songdb and our emulator give the same number,
so this replaces a measurement rather than competing with one. The last row is the part the
measurement cannot give at all.

## What it is not

**Not a source for the consoles, SID, SNDH, ZX Spectrum or Atari 8-bit.** songdb holds only what
audacious-uade plays. Its Modland source has 96,155 rows through UADE, 45,299 through ft2play and
the rest through tracker players, and **zero** `.nsf`, `.gbs`, `.kss`, `.hes`, `.ay`, `.spc`,
`.vgm`, `.sndh`, `.ym`, `.sap` or `.pt3`. An earlier message in this project guessed otherwise
before measuring; the measurement is what stands. C67's console tunes without a length stay
without one.

**Not a change for anything that knows its own length.** The rule at open is already "the file
wins": `PlaybackController` asks the backend first and a database only when the backend has
nothing. libopenmpt's MOD and XM keep their own figures.

## The data

`tsv/pretty/md5/songlengths.tsv`, 11.9 MB, **GPL-2.0-or-later** (`docs/LICENSES.md`, checked
2026-09-07; the generator carries the SPDX line). One line per file:

```
001a02867da0	0	128240,l 5840,s 3360,s 3340,s 3060,s
```

The **first 48 bits of the MD5** as twelve hex characters — the key `track_metadata` already uses,
and the app already hashes every opened file once for both databases. Then the first subsong's
number (0 or 1), then one `milliseconds,end` per subsong, in order. A third field of `!` marks a
subsong that duplicates another.

476,919 rows, 522,218 subsongs, 11,152 files with more than one. **How each ended**, from
`audacious-uade/src/common/songend.h` rather than guessed from the letters, over every subsong:

| code | meaning | count | used as a length? |
| --- | --- | --- | --- |
| `p` | the replay routine reported the end | 351,823 | **yes** |
| `p+s` | the routine's end, trailing silence trimmed | 128,856 | **yes** |
| `p+v` | the routine's end, fade-out trimmed | 19,500 | **yes** |
| `s` | sound stopped and stayed stopped | 6,573 | **yes** |
| `l` | a loop was detected; the length is one pass | 6,527 | **yes** — see D4 |
| `r` | a repeat was detected | 131 | **yes** |
| `v` | faded out | 29 | **yes** |
| `l+s`, `l+v` | a loop, trimmed | 22 | **yes** |
| `n` | the subsong makes no sound | 6,881 | no — an empty subsong, D3 |
| `e` | error | 1,706 | no |
| `t` | timeout | 170 | **no** — a cap, not a length; C67, and A44's 512-second trap |

## Decisions that are the owner's

**D1. One download or two.** songdb's metadata table already downloads under "Track metadata",
from the same repository. Recommended: **the same tick**, relabelled "Track metadata and lengths" —
one idea, "what songdb knows about a file", and not a second box whose purpose needs explaining.
The alternative is a separate tick for 11.9 MB.

**D2. Pinned or `master`.** The metadata URL follows `master` today. The README says the author
"reserve[s] the right to change the format or location … at any time". Recommended: **pin both
files to one commit** (`1bad3e8`, 2026-08-22, the one measured here), the way sc68's replays and
UADE's players are pinned, and move the pin deliberately.

**D3. Empty and duplicate subsongs in "play all".** 6,881 subsongs make no sound and 3,758 repeat
another. Skipping them would make "play all" play music rather than gaps. Recommended: **a later
step**, once lengths are in and the skip can be judged on the phone — it changes what a user hears,
where lengths only change what they see.

**D4. What a loop's length means.** For `l` the length is one pass, and the player already ends a
tune at a known length (the rule HVSC's SID lengths follow). So a looping tune would play once
through and move on, where today it plays until UADE's own 512-second cap. Recommended: **yes, one
pass** — it is what every player using these databases does, and the fallback length in Settings
still governs the tunes nothing knows.

## The design

**Storage: `songdb_lengths`, schema version 17.** Reserved here, before any code, so no other
branch claims it (`/mnt/workspace/AGENTS.md` §10).

```sql
CREATE TABLE songdb_lengths (
    key INTEGER PRIMARY KEY,        -- the 48-bit prefix, as a number
    first_subsong INTEGER NOT NULL,
    subsongs TEXT NOT NULL          -- the file's own "ms,end ms,end …", kept as published
)
```

**The key is an integer, and that halves the cost.** Measured with SQLite on the full file: a
twelve-character `TEXT` key, the shape `track_metadata` uses, takes **25.0 MB**; the same prefix as
an `INTEGER PRIMARY KEY` — which fits, 48 bits in 64, and *is* the rowid — takes **11.1 MB**, with no
separate index. `track_metadata` could take the same change later; not in this stage.

**Kept as published, decided at read.** The `subsongs` column holds the source text, and the end
codes are interpreted when a file is opened, by one pure function. A policy change — D3, D4, a code
added upstream — is then a code change and not a re-download.

**At open**, after the backend has been asked and has nothing (the existing rule):

1. HVSC by the full MD5 — SIDs, as now;
2. **songdb by the first twelve characters** — new, same hash, no second pass over the bytes;
3. for UADE, the background measurement — **only if 1 and 2 had nothing**, so a tune songdb knows
   costs no second emulator at all;
4. the fallback length in Settings, as now.

The list goes into `openSongLengths`, which `selectSubsong` already reads per subsong. songdb's
first entry is the first subsong UADE reports, both being the same program's numbering; the
paradroid check above is seven subsongs agreeing in order.

**The engine needs to be told** when a length is known, so the measurement does not start: one
call before `start`, `Track.lengthsKnown()`, which `UadeBackend` answers by not measuring. Every
other backend ignores it.

## The steps, each one checkable

1. **Parser, pure Kotlin, no Android.** `SongDbLengths.parse(line)` → first subsong and a list of
   (seconds, end, duplicate). `SongDbLengthsTest` on real lines from the file — every end code, a
   `!`, a one-subsong and a twenty-one-subsong row — and on what must be refused: `t`, `e`, `n`,
   a zero length, a malformed row. *Checked: unit tests.*
2. **The precedence rule, pure.** `LengthSource.choose(backend, hvsc, songdb, …)` as a function, with
   a test per row of the list above — including a MOD whose backend knows its length and whose
   songdb row disagrees, where the file must win. *Checked: unit tests.*
3. **Schema 17 and its migration**, with the test `/mnt/workspace/AGENTS.md` §10 requires: a real
   SQLite database built at 16, rows in it, migrated, rows intact. *Checked: migration test.*
4. **Download and import** on the metadata tick (D1), pinned (D2), streamed into the table in
   batches like `track_metadata`, counted, shown in storage with a delete. Sizes in `DownloadSizes`:
   the everything figure grows by 12 MB. *Checked: the existing download tests, and the phone.*
5. **Use it at open and skip the measurement.** *Checked on the host*: `probe-uade-engine.py` gains
   a songdb pass — for every one of its 140 files, the songdb length against the driver's measured
   one, failing on any `p`-type disagreement over 0.2 s. *Checked on the phone*: `amberstar (16).hipc`
   shows 5:08 at once rather than after two seconds; a tune that ends in `l` shows a length and ends
   at it.
6. **A50, folded in.** What the background measurement learns for a file songdb does not know — a
   tune in a granted folder — is written to the same shape of table under the full MD5, so the
   second play is instant too. Separate step because it needs its own writer and its own
   questions (how much to keep, whether a deleted download takes it along).

## What it costs

| | |
| --- | --- |
| download | +11.9 MB, on request, with the metadata |
| storage | +11.1 MB in the database |
| schema | one migration, 16 → 17 |
| per tune | one indexed lookup on a hash already computed |
| saved per tune | a second emulator and a few seconds of a core, for every tune songdb knows |

**Phone only.** The page cannot play these formats at all (A44), so there is nothing for it to show
a length for, and `docs/SPEC_RANDOM.md` parity does not reach this.
