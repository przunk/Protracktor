*A cloud review (`/ultrareview`) of everything on `develop` that `master` does not have yet:
42 files, ~1,510 lines added and ~430 removed. Most of it is History a page at a time, History that
keeps every tune, and C91's SAP lengths.*

It found four things: one fault and three nits. **Nothing here is fixed yet.** Each finding below
says what was checked against the code, and how.

## F1. Clearing History can put the cleared tunes back on screen — **confirmed by reading the code; FIXED and merged 2026-09-28; the owner tests it in use**

`PlaybackController.clearHistory()` deletes the rows and then empties the list. It does not stop a
read of History that is already running, and there are two of those:

- **`showHistoryPage()`**, which runs as `historyRead`. When it finishes, it keeps its rows only if
  the page it read is still the page on screen. `clearHistory()` sets the page to 0, so a read of
  page 0 still passes that check. This is the case the review reported.
- **`openHistory()` → `refreshHistory()`**, which runs in a plain `scope.launch` that is not tracked
  anywhere. When it finishes, it checks only that History is still open. It then writes
  **`historyTotal` as well as the rows**. This one is worse than the case the review reported,
  and the review did not mention it: the count comes back along with the tunes.

**How it happens.** The user opens History or turns a page and taps *Clear History* before the page
has loaded. The read started first and has already got its rows. If it finishes after the delete,
it overwrites the empty list. The database is empty, but the screen shows the old page, and after
`refreshHistory()` it shows the old count too. The tunes stay on screen until History is left and
opened again.

**Why it is more likely now.** The same diff turns on WAL (`setWriteAheadLoggingEnabled(true)`). A
read then no longer waits for the delete to finish, so the two can run at the same time. The window
is short, but it grows with History, and History no longer has a size limit.

**Fix, proposed:**
- Track both reads as `historyRead`, and cancel it at the start of `clearHistory()` and
  `openHistory()`.
- Better still, have each read drop its result when a newer request has been made since it started.
  A cancel alone does not stop a read that has already reached its `_browse.update`.
- Add a test that fails before the fix.

**Status: fixed.** Opening, turning a page and clearing now go through `HistoryReads`: every request
takes a number, and a read shows what it found only if no newer request came since it began --
cancelling alone would not stop a read that already has its rows. `HistoryReadsTest` holds a read open
across a clear, for a page turn and for an opening; both fail without the check. One correction to
the finding: the opening read cannot be raced from the screen today, since *Clear history* appears
only once History has loaded; it is covered all the same.

## F2. Web History keeps everything, and reads everything on every visit — **confirmed by reading the code; FIXED and merged 2026-09-28; the owner tests it in use**

`web/src/store.js`: `played.record()` no longer removes old rows, so the 500-row limit is gone.
`played.recent()` still loads the whole store with `getAll()` and sorts it in JavaScript, and
`app.js` shows one page of 100 from that. So opening History on the page gets slower with every tune
played, with no limit.

The phone had exactly this problem and fixed it in the same diff by reading one page at a time
(`SchemaSql.PLAY_HISTORY_PAGE`). The web page did not get the same fix.

**Fix, proposed:** an index on `playedAt`, read backwards with a cursor, skipping to the page's
offset; and `count()` for the total. The `played` store has no such index yet, so adding one means
an IndexedDB version bump.

**Severity:** a nit today, because it only gets slow over months of use. It will get worse on its
own.

**Status: fixed.** The page's database is version 4, with a `playedAt` index on `played`; History reads
its count and one page backwards along it (`played.count`, `played.page`). `check-web-store-upgrade.mjs`
opens a version-3 database holding playlists and History with the new code: both kept, History paged.
Without the index it fails.

## F3. A SAP's measured length is remembered for only one subsong — **confirmed by reading the code; to `WISHLIST.md` B40, 2026-09-28**

`native/engine/engine.cpp`, `AsapBackend`: `measured_` is a single packed `(subsong, ms)` slot.
Switching back and forth between two subsongs that have no `TIME` and are not in songdb starts the
measurement again every time. Nothing breaks; the cost is CPU and battery.

**Proposed:** a small cache keyed by subsong, or leave it. This is a wishlist item, not a defect.

## F4. `HistoryPages` names functions that `rules.js` does not have — **confirmed; FIXED and merged 2026-09-28**

`HistoryPages.kt:11` refers to `pageOf`/`pageRange` in `rules.js`. The functions there are
`historyPageCount`, `historyPageClamp` and `historyPageRange`. This matters more than a normal
comment slip, because this comment is how someone keeping the Kotlin and JS rules in step finds
the JS side.

**Fix:** a one-line comment change. It can go on F1's branch.
